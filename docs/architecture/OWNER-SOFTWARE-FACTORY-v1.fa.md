## ۱. مرز محصول

**ورودی:** توصیف آزاد کاربر، محدودیت‌های واقعی، پاسخ به پرسش‌های ضروری، تغییرات بعدی.

**خروجی:** کد منبع قابل اجرا، بستهٔ راه‌اندازی، راهنمای فارسی، داده/مهاجرت، آزمون‌های واحد و یکپارچه، گزارش امنیت/محدودیت، وضعیت تحویل و شواهد پذیرش.

**چرخهٔ ضروری:** فهم نیاز → تثبیت معیارها → طراحی معماری → تقسیم وظایفِ وابسته → پیشنهاد تغییر → اجرا در محیط مجاز → ارزیابی مستقل → اصلاح/بازیابی → تجمیع → تحویل → توسعهٔ نسخهٔ بعد.

**خارج از دامنهٔ کنونی:** فروش خود CSEF، صدور فاکتور و اشتراک برای مشتریان آن، چندمستاجری، خوشهٔ سرویس‌ها، انتشار بدون اجازه، هزینهٔ API بدون تأیید و اجرای آزاد کد نامطمئن روی میزبان.

## ۲. ساختار ساده با یک مرکز تصمیم

    کاربر (شرح‌حال ساده / تغییر نیاز)
          ↓
    لایهٔ تعامل [CLI موجود | UI محلی آینده | MCP مشروط]
          ↓
    سرویس کاربردی CSEF / Workflow موجود
          ├── ProjectBook + پایگاه SQLite مشترک: هدف، نسخه، تصمیم، سؤال، journal، lease
          ├── برنامه‌ریز: تبدیل نیاز به مشخصات و گراف وظایف
          │      └── آداپتر Spec Kit موجود: اسناد spec / plan / tasks (پیشنهاد، نه حقیقت پذیرفته)
          ├── بستهٔ زمینهٔ نسخه‌بسته، مسیر نیاز ← تسک ← آزمون
          ├── انتخاب مدل و سیاست هزینه
          │      ├── OpenAI Responses (آداپتر موجود)
          │      ├── Anthropic Messages (آداپتر موجود)
          │      └── Codex CLI (اختیاری، آداپتر میراثی)
          ├── نویسندهٔ تغییر محدود: candidate Git worktree
          ├── ExecutionProvider: guest ایزولهٔ آزموده‌شده [موجود نیست]
          │      └── Docker reviewed موجود: فقط REVIEW، هرگز PASS
          ├── Gate مستقل موجود: آزمون/شاهد/کنترل نسخه/اختیار checkpoint
          └── بستهٔ تحویل: کد، آزمون، دستور اجرا، نسخه، محدودیت
                ↓
          برنامهٔ قابل استفاده، بدون ارتقای خودکار یا ادعای بی‌سند

**اصل مهم:** این‌ها مسئولیت‌های منطقی‌اند، نه هشت سرویس یا هشت عامل مستقل. کنترل‌کنندهٔ Python + یک SQLite + آداپترهای مقصد کافی است تا زمانی که آزمون نیاز واقعی دیگری را اثبات کند. از یک مدل برای خروجی مشترک استفاده شود و تکرار پردازش بی‌دلیل حذف شود.

## ۳. دو نوع تقسیم کار که نباید اشتباه گرفته شوند

الف) **Backlog ساخت خود CSEF**: ۳۸ تسک T001 تا T038 با وابستگی بدون چرخه، از قبل تعریف شده‌اند؛ T001 تا T007 دارای شواهد اتمام نمونهٔ اولیه‌اند. گراف این تسک‌ها برنامهٔ توسعهٔ CSEF است، نه قابلیت تقسیم وظیفهٔ عمومی برای پروژه‌های کاربران.

ب) **Task Graph پروژهٔ کاربر**: هنوز به‌صورت یک برنامه‌ریز عمومیِ اجراشده با تضمین کامل موجود نیست. جریان فعلی Workflow مراحل ترتیب‌دار ۶ تا ۲۴گانه دارد؛ در کد، سه جایگاه اول سندمحور و بقیه کدمحورند. این جریان با «گراف پویا و قابل به‌روزرسانی وظایف هر نرم‌افزار» یکی نیست.

**قرارداد پیشنهادی هر وظیفهٔ پروژهٔ کاربر:**

| فیلد | ضرورت |
| --- | --- |
| شناسه و نسخهٔ هدف | پیوند با ProjectBook و عدم استفاده از درخواست کهنه |
| شناسه‌های نیازمندی/تصمیم | جلوگیری از گم‌شدن هدف هنگام خردکردن |
| وابستگی‌ها و پیش‌شرط‌ها | زمان‌بندی درست بدون اجرای زودهنگام |
| مالکیت فایل و دامنهٔ تغییر | جلوگیری از تداخل دو نویسنده |
| ورودی‌ها / بستهٔ زمینه | نیاز و قرارداد لازم، بدون توزیع تمام مکالمه |
| خروجی قابل مشاهده | کد یا سندی که واقعاً تحویل می‌شود |
| معیار پذیرش از پیش تصویب‌شده | توقف ادعای قبولی خود عامل |
| اثر بر تسک‌های بعد و قراردادها | ابطال نسخهٔ کهنه و تست رگرسیون |
| سقف تعداد تلاش/زمان/هزینه | جلوگیری از حلقهٔ بی‌پایان |
| نتیجهٔ اجرا و مرجع شاهد | PASS / FAIL / REVIEW / UNKNOWN / STALE، با منشأ کنترل‌کننده |

گراف باید پوشش کامل نیازمندی‌های پذیرفته، نبود چرخه، وابستگی واقعی، برش عمودی قابل اجرا و آزمون یکپارچه را بررسی کند. تقسیم زیاد تسک‌ها بدون تضمین اتصال اجزا، موفقیت نیست. هر تسک را فقط پس از آماده‌بودن وابستگی‌هایش آغاز می‌کنیم؛ هم‌زمانی یک قابلیت اختیاری است نه پیش‌فرض، و یک worktree هرگز دو نویسنده ندارد.

## ۴. قراردادهای قابل توسعه بدون تغییر هسته

| قرارداد | وضعیت امروز | مالک اختیار |
| --- | --- | --- |
| مدل ساختاریافته (StructuredClient / DirectAPI) | موجود؛ دو پروتکل مستقل، آزمون پاسخ شبیه‌سازی‌شده | مدل پیشنهاد می‌دهد، کنترل‌کننده می‌پذیرد |
| عامل پیشنهاد تغییر (CodingAgent / DirectAPIAgent) | موجود؛ برنامهٔ کامل توسعهٔ پروژه هنوز ثابت نشده | Gate و محدودهٔ فایل |
| اسناد Spec Kit | آداپتر import/export موجود؛ متن واردشده صرفاً پیشنهاد است | ProjectBook و تصمیم صاحب پروژه |
| برنامه‌ریز Task Graph نسخه‌دار | توسعه و آزمایش سرتاسری لازم است | کنترل‌کننده + معیارهای تصویب‌شده |
| بستهٔ زمینه و ردیابی نیاز تا کد | جزئی و طراحی‌شده؛ پوشش کامل اثبات نشده | ProjectBook |
| اجرای ایزوله (ExecutionProvider) | Docker reviewed-only؛ مرز VM مستقل هنوز ساخته/سنجیده نشده | زیرساخت قابل اعتماد |
| ارزیابی و پذیرش (Gate) | نمونهٔ اولیه با آزمون‌های واقعی + حد امنیتی fail-closed | فقط کنترل‌کننده و harness |
| تحویل / بازیابی / رابط وب | ناقص یا طراحی؛ نباید آماده ادعا شوند | سرویس کاربردی و کاربر |

آداپتر هر ابزار بیرونی باید قرارداد نسخه‌دار، مسیر دادهٔ محدود، آزمون‌های خطا/قطع و مجوز استفادهٔ روشن داشته باشد؛ هیچ خروجی افزونه اجازهٔ PASS، تغییر سیاست یا تغییر هدف پذیرفته‌شده ندارد.

## ۵. راهبرد استفادهٔ مجدد، نه کدنویسیِ دوباره

1. **Spec Kit موجود:** قبل از ایجاد موتور planning جدید، اتصال فعلی و قالب‌های پین‌شده‌اش با یک نمونهٔ واقعی امتحان شود. اگر کار مشخصی را پوشش می‌دهد، فقط Mapping کمبودها نوشته شود.
2. **BMAD:** فقط الگوهای تحلیلی/تحویلی مفید در صورت شکاف واقعی، نه orchestrator دوم و نه دو منبع حقیقت.
3. **عامل کدنویسی موجود:** ابتدا DirectAPIAgent حاضر، سپس در صورت اثبات نیاز آزمایش SDKهایی مانند OpenHands، صرفاً پشت CodingAgent؛ نه بازنویسی Gate.
4. **SQLite، Git، pytest و قالب‌های فعلی:** دوباره استفاده شوند. نصب API gateway، صف، بردار DB، مدل محلی یا سرویس دیگر بدون نیاز مشخص ممنوع.
5. قبل از هر استفاده از کد/دادهٔ بیرونی، نسخه و مجوز همان جزء تأیید و شرایط attribution حفظ شود. قابل مشاهده بودن مخزن مجوز کپی نیست.

## ۶. امنیت، اختیارات و بازیابی

- کلید API فقط در محیط مورد اعتماد؛ هرگز در promptهای مخزن/لاگ/runner تولیدی یا خروجی قابل دانلود.
- کد تولیدشده نباید policy، آزمون پذیرش منجمد، journal، دادهٔ کاربر یا فایل‌های خود CSEF را تغییر دهد.
- تا وقتی مرز VM با آزمون واقعی فایل/شبکه/فرایند/نشت رمز تأیید نشده، اجرای reviewed-only فقط REVIEW است؛ PASS و انتشار ممنوع.
- درخواست‌های بیرونیِ با نتیجهٔ نامعلوم، بدون reconciliation نباید خودکار تکرار شوند؛ intent پیش از فراخوانی و outcome پس از آن ثبت شود.
- مدل نمی‌تواند به تنهایی معیارهای پذیرش یا نسخهٔ هدف را جابه‌جا کند. تغییر هدف با تأیید صاحب پروژه، نسخهٔ جدید، تحلیل اثر و ابطال شواهد قدیمی انجام می‌شود.
- هزینه‌ها با سقف صریح، رسید مصرف و متوقف‌سازی قابل کنترل باشند؛ نامعلوم برابر صفر نیست. هیچ اقدام پولی یا استقرار بیرونی بدون مجوز انجام نمی‌شود.
- نسخهٔ کار روی branch/worktree جدا؛ بازگشت صرفاً تغییرات تحت مالکیت همان اجرا؛ وضعیت dirty کاربر حفظ شود.
- از یک مسیر اجرای کاربردی برای CLI و UI استفاده می‌شود؛ UI یا MCP حق مستقیم برای نوشتن پایگاه یا اعطای checkpoint ندارند.

## ۷. مرز آزمون و ادعا

۳۸ تسک موجود گراف قابل‌قبولی برای **توسعهٔ CSEF** دارند. موفقیت ۲۶۰ آزمون در CI برای نسخهٔ انتقال‌یافته، تضمین صحت چرخهٔ ساخت پروژهٔ واقعی نیست. دو API آزمایش قرارداد شبیه‌سازی‌شده دارند؛ آزمایش زنده با کلید مالک هنوز مدرک ندارد. اتصال کامل یک پروژهٔ چندماژولی، بازیابی از قطع در تمام مرزها، guest امن و داشبورد نیز ثابت نشده‌اند.

برای خروج از نمونهٔ اولیه باید یک درخواست ساده به **نرم‌افزار واقعی قابل نصب** تبدیل شود: پایگاه داده و احراز هویت، دو یا چند ماژول وابسته، UI، آزمون‌های سرتاسری، تغییر نیاز پس از نسخهٔ اول، backup/restore، و فهرست محدودیت‌ها. آزمونِ فقط «تعداد فایل/تسک» یا «سبزشدن تست‌های ساختگی» کافی نیست.

هیچ قابلیت «توسعهٔ خودکار خود CSEF» مجاز نیست که کنترل‌کننده یا معیار پذیرش خود را در همان اجرای تحت آزمون تغییر دهد. تغییرات خودتوسعه تنها به PR با بازبینی انسانی می‌رسند.
