# CSEF — نقشهٔ راه اجرایی ابزار شخصی تولید نرم‌افزار (v1)

**تاریخ:** ۲۰۲۶-۱۱-۱۷ · **وضعیت:** طرح پیشنهادی، نه اجرای کامل · **مخزن مجاز:** فقط `ebrahimism/CSEF-Execution-Agent`.

اسناد مرجع: [معماری](../architecture/OWNER-SOFTWARE-FACTORY-v1.fa.md) · [نگاشت ماشین‌خوان ۳۸ تسک](execution-map-v1.json) · [backlog تاریخی](backlog.json).

## هدف نهایی و ملاک پذیرش

این سیستم ابزار **شخصی** کاربر برای بناکردن کسب‌وکار نرم‌افزاری با حداقل سرمایه است؛ خود CSEF قرار نیست فروخته شود. از یک شرح‌حال ساده باید به نیازمندی و تصمیم نسخه‌دار، معماری، تقسیم پویا و وابستگی‌محور کار، تولید کد، آزمون مستقل، اصلاح و ادامه بعد از وقفه، یکپارچه‌سازی، و محصول واقعیِ قابل نصب و تحویل برسیم. **کیفیت و کامل‌بودن مقدم بر ارزان‌ترشدن** است؛ هزینه باید شفاف و با سقف مجاز کنترل شود.

اصل ثابت: کمترین پیچیدگی، بیشترین استفادهٔ مجدد، عدم تضعیف امنیت/آزمون/ممیزی/بازیابی، افزونه و آداپتر به‌جای بازنویسی هسته. از کد متن‌باز فقط با مجوز معتبر و حفظ انتساب استفاده می‌کنیم.

## یافته‌های ممیزی تقسیم وظیفه

۱. **تقسیم ساخت خود CSEF:** در `backlog.json` تعداد **۳۸ تسک یکتا** وجود دارد؛ وابستگی‌ها بدون چرخه و بدون شناسهٔ ناشناخته‌اند. این تقسیم از نظر **گراف برنامه‌ریزی معتبر** است؛ این موضوع کیفیت یا کافی‌بودن خود تسک‌ها را ثابت نمی‌کند.

۲. **تفاوت با تقسیم پروژه‌های مشتری:** کد `workflow/stages.py` و `workflow/engine.py` فعلاً گردش‌کار **۶ تا ۲۴ مرحلهٔ ترتیبی** را اجرا می‌کنند؛ سه جایگاه اول سندمحور است. این هنوز یک **Task Graph عمومی** برای خردکردن پویا و سازگار با نیازهای هر نرم‌افزار، مدیریت مالکیت فایل و پوشش نیاز تا تست نیست؛ S1 و S3 باید این شکاف را ببندند.

۳. **تعارض وضعیت:** تمام ۳۸ مورد در backlog با `planned` ثبت شده‌اند، ولی گزارش‌های اجرای قبلی T001–T007 را برای *برش نمونهٔ اولیه* تکمیل‌شده می‌دانند؛ در مخزن جدید نیز دو API مستقیم و smoke test پیاده شده‌اند. بنابراین **وضعیت اجرا را از شواهد بگیریم، نه از فیلد قدیمی planned**. سوابق پاک یا بازنویسی نشوند.

۴. **شواهد:** در مبنای این طرح CI تعداد **۲۶۰ آزمون موفق** داشته؛ این‌ها عمدتاً رگرسیون و آزمایش‌های شبیه‌سازی هستند. دو API با اعتبارنامهٔ واقعی کاربر آزمایش نشده‌اند؛ Docker بررسی‌شده صرفاً `REVIEW` می‌دهد؛ محیط VM ایزوله و محصول نهایی ساخته نشده‌اند.

## اجرای پیشنهادی در ۸ مرحله

| فاز | تسک‌های موجود | نتیجهٔ قابل تحویل | دروازهٔ عبور |
|---|---|---|---|
| **S0 — تثبیت هدف و خط مبنا** | T001–T007 | ثبت رسمی هدف جدید، تطبیق رسیدهای قدیمی با کد جدید، وضعیت آزمون‌ها | برنامه/هدف نسخه‌دار، سوابق سالم، CI سبز؛ هیچ اتمام جعلی |
| **S1 — شرح‌حال تا گراف کار** | T009–T012 | سؤال‌های ضروری، مشخصات و معماری واحد، Spec Kit موجود، Task Graph واقعی | نیازهای پذیرفته‌شده بدون حذف؛ هر تسک با شناسه، وابستگی، scope، قرارداد و معیار آزمون؛ نبود چرخه |
| **S2 — دو API و سقف مصرف** | T013–T017 | OpenAI و Anthropic واقعی، رسید مصرف و وضعیت قابلیت‌ها، تنظیم سقف هزینه | آزمون زندهٔ هر API با کلید خصوصی کاربر؛ خطا و timeout ایمن؛ هیچ هزینهٔ نامعلوم = صفر؛ T017 فقط در صورت نیاز |
| **S3 — تغییر کد و ادامهٔ کار** | T008, T018–T020 | اجرای تسک محدود به نسخهٔ خاص، worktree جدا، بازیابی قطع و تحلیل اثر | عدم تغییر خارج scope، عدم تکرار اثر نامعلوم و عدم پذیرش نسخهٔ کهنه |
| **S4 — اجرا و داوری مستقل** | T021–T028 | ExecutionProvider امن، آزمون مرز شبکه/فایل، Gate و شاهد مستقل | تا ایزوله‌سازی واقعاً آزموده نشود `PASS` ممنوع؛ آزمون تقلب در گزارش/معیار و توقف واقعی |
| **S5 — یکپارچه‌سازی و تحویل** | T031–T034 | پروژهٔ چندماژولی با پایگاه داده/UI/API، تست سرتاسری، بسته نصب، backup/restore | نصب تمیز، کارکرد واقعی همهٔ اجزا، حفظ داده و گزارش نقص‌ها |
| **S6 — رابط شخصی** | T029–T030 | رابط فارسی و/یا اتصال چت روی همان سرویس کاربردی موجود | UI و CLI رفتار واحد و کنترل دسترسی واحد؛ بدون DB/سرویس اضافی |
| **S7 — اثبات کار و نصب داخلی** | T035–T038 | اولین پروژه از شرح‌حال ساده تا نرم‌افزار قابل استفاده، سپس تغییر نیاز و آزمون مجدد | محصول قابل اجرا و مستند؛ بازیابی، رگرسیون و بررسی نیازمندی‌ها؛ T037/T038 در صورت نیاز واقعی |

**وابستگی اجرایی:** `S0 → (S1 و S2) → S3 → S4 → (S5 و S6) → S7`. فازهای هم‌سطح فقط با scope مستقل و بدون دو نویسندهٔ هم‌زمان بر یک worktree قابل پیش‌برد هستند. ترتیب داخلی تسک‌ها هم تابع `depends_on` در backlog موجود است، نه شمارهٔ فاز.

## معماری بدون تکرار

```text
شرح‌حال کاربر → ProjectBook / Questions / Decisions (SQLite موجود)
                        │
                        ├─ Spec Kit bridge موجود → spec / plan / task proposals
                        ├─ Task Graph نسخه‌دار + بستهٔ زمینه / قرارداد
                        ├─ Structured Model Client → OpenAI / Anthropic / Codex اختیاری
                        ├─ CodingAgent → تغییر محدود در candidate worktree
                        ├─ ExecutionProvider → guest امن (الزام برای PASS)
                        ├─ Gate مستقل → آزمون، شواهد، checkpoint با اختیار کنترل‌کننده
                        └─ Delivery → برنامه، تست، نصب، محدودیت‌ها
                               ↑
                  CLI / رابط فارسی / اتصال چت
```

این‌ها **مسئولیت‌های منطقی** هستند، نه سرویس‌های موازی جدید. SQLite مشترک و هستهٔ Python موجود حفظ می‌شوند. ابزار خارجی فقط به‌صورت آداپتر/قالب و بدون اختیار تأیید به سیستم وصل می‌شود.

## استفادهٔ مجدد قبل از کدنویسی

- از `src/csef_gate/integrations/spec_kit.py` برای تبادل اسناد موجود استفاده کنیم؛ موتور planning دوم را کپی نکنیم. خروجی import فقط پیشنهاد است.
- الگوهای مفید BMAD فقط وقتی شکاف مستند وجود دارد؛ نه استقرار orchestration موازی.
- `DirectAPI` و `DirectAPIAgent` موجود برای پیشنهاد کد کافی‌اند تا زمانی که آزمون ضرورت عامل دیگری مثل OpenHands SDK را نشان دهد.
- `Git`، `SQLite`، `pytest` و Gate فعلی دوباره استفاده شوند؛ سرویس صف، پایگاه برداری، gateway و Docker daemon جدید بدون نیاز اثبات‌شده راه‌اندازی نشوند.

## قواعد ثابت اجرای هر مرحله

برای هر تسک: **ورودی نسخه‌دار، شناسهٔ نیاز، وابستگی‌های معتبر، محدودهٔ نوشتن، معیار پذیرش منجمد، خروجی قابل مشاهده، آزمون جاری، ثبت خطا و نحوهٔ ادامه** الزامی است. هر تغییر نیاز باید اثرش بر تسک‌های قبلی و آزمون‌ها را مشخص و در نسخهٔ جدید ثبت کند.

تکمیل هر مرحله فقط با شواهد همان نسخه مجاز است: آزمون‌های مرتبط و رگرسیون، گزارش جدایی کنترل‌پلین و محیط اجرا، خروجی قابل استفاده، و محدودیت‌های صریح. اجرا بدون کلید واقعی یا sandbox آزموده‌شده هرگز موفقیت زنده یا تأیید امنیت تلقی نشود. هیچ خودتوسعه‌ای حق دستکاری کنترل‌کننده یا معیار ارزیابی همان اجرای خودش را ندارد.

## شروع عملی پس از پذیرش طرح

۱. **S0** را به‌جای بازاجرای بی‌مورد T001–T007، با تطبیق رسیدها و ثبت نسخه‌دار تغییر اولویت مالک آغاز کنیم.  
۲. **S1** را با نمونهٔ واقعیِ متن ساده و Spec Kit موجود شروع کنیم. برای یک محصول کوچک دارای DB و UI، گراف تسک با تست تمام مسیر بسازیم؛ از این نمونه برای ارزیابی طراحی استفاده کنیم.  
۳. **S2** را پس از فراهم‌شدن کلیدهای خصوصی صاحب پروژه با یک smoke test واقعی پیش ببریم؛ بدون ارسال کلید در GitHub یا چت.  
۴. از مراحل بعد فقط بعد از عبور از دروازهٔ وابستگی قبلی حرکت کنیم؛ هیچ تسکی صرفاً به دلیل سبزبودن تست‌های واحد «محصول تحویل‌شده» نیست.

## حیطهٔ مجاز

**فقط** مخزن `CSEF-Execution-Agent`. مخزن `csef-builder` برای این برنامه **خواندنی/تاریخی** است و هیچ ویرایش یا PR در آن انجام نشود. در این مرحله فقط اسناد معماری، نگاشت و تسک GitHub ساخته می‌شوند؛ توسعهٔ هسته، VM، خرج API، استقرار و UI به مراحل بعد موکول است.

هیچ تخمین قطعی زمان/هزینه، درصد پیشرفت یا ادعای آماده‌بودن محصول بدون آزمون عملی ارائه نشده است.
